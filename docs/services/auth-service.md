# 🔐 auth-service

Servicio de **usuarios y autenticación**. Es el único emisor de JWT del sistema: registra usuarios, valida credenciales, emite tokens HS256 y publica los eventos de usuarios en Kafka.

- **Puerto:** `8081`
- **Base de datos:** `authdb` (PostgreSQL)
- **Tests:** 27

## Responsabilidades

1. **Registro** de usuarios (`POST /api/users`)
2. **Login** con username *o* email + contraseña bcrypt → emisión de JWT
3. **Perfil**: consulta pública, edición de perfil/datos de cuenta
4. **Baja** de cuenta (soft-delete lógico con `active = false`)
5. **Publicación** de eventos `user.registered` / `user.deactivated` en el topic `user-events`

## Diagrama de flujo de autenticación

```mermaid
sequenceDiagram
    autonumber
    participant FE as Frontend
    participant A as auth-service
    participant DB as authdb
    participant K as Kafka

    FE->>A: POST /api/users/login {identifier, password}
    A->>DB: busca usuario activo por username o email
    A->>A: verifica contraseña con BCryptPasswordEncoder
    A-->>FE: 200 { token, tokenType: Bearer, expiresIn: 86400, user }
    Note over FE: Guarda el token; lo envía en Authorization para el resto de llamadas

    FE->>A: POST /api/users {username, email, password}
    A->>A: valida unicidad de username y email
    A->>DB: INSERT users (password encriptada con bcrypt)
    A->>K: publish("user-events", "user.registered", {userId, username})
```

## Modelo de datos (`authdb`)

```sql
CREATE TABLE users (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username    VARCHAR(30)  NOT NULL,
    email       VARCHAR(255) NOT NULL,
    password    VARCHAR(255) NOT NULL,
    display_name VARCHAR(30),
    bio         VARCHAR(500),
    avatar      VARCHAR(300),
    active      BOOLEAN NOT NULL DEFAULT TRUE,
    created_at  TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_users_username UNIQUE (username),
    CONSTRAINT uk_users_email UNIQUE (email)
);
```

- Migración Flyway: `V1__create_users.sql`.
- `active = false` es una **baja lógica**: el usuario queda oculto para lecturas y login, pero el registro no se elimina (se conserva para auditoría).

## API

### Públicas (no requieren token)

| Método | Ruta | Descripción |
|--------|------|-------------|
| `POST` | `/api/users` | Registro (`username`, `email`, `password`, `displayName?`) |
| `POST` | `/api/users/login` | Login → `LoginResponse` con JWT |
| `GET` | `/api/users` | Listar usuarios activos (filtro opcional `username`) |
| `GET` | `/api/users/{id}` | Perfil público de un usuario activo |

### Autenticadas (requieren `Authorization: Bearer <JWT>`)

| Método | Ruta | Descripción |
|--------|------|-------------|
| `PUT` | `/api/users/me` | Actualizar perfil (`displayName`, `bio`, `avatar`) |
| `PUT` | `/api/users/me/password` | Cambiar contraseña (comprueba la actual) |
| `PUT` | `/api/users/me/email` | Cambiar email |
| `PUT` | `/api/users/me/username` | Cambiar username |
| `DELETE` | `/api/users/me/account` | Dar de baja la cuenta (pide contraseña) |

### Ejemplos

**Registro** `POST /api/users`

```json
{
  "username": "marc",
  "email": "marc@example.com",
  "password": "secret123",
  "displayName": "Marc"
}
```

**Login** `POST /api/users/login`

```json
{ "identifier": "marc", "password": "secret123" }
```

## Seguridad

- Estrategia **stateless** (sin sesiones): cada petición lleva su JWT.
- `SecurityConfig` (`auth/config/SecurityConfig.kt`):
  - Públicas: `POST /api/users|/api/users/login`, `GET /api/users/**`, `/actuator/**`.
  - Cualquier mutación sobre `/api/users/me/**` queda protegida.
- Contraseñas encriptadas con **BCrypt** (`BCryptPasswordEncoder`, bean en `PasswordConfig`).
- El JWT se firma con HS256 y la misma clave compartida `app.jwt.secret` que el resto de servicios (`shared/security/JwtSecurityConfig.kt`), con claims:
  - `sub` = `userId` (identidad canónica para los demás servicios)
  - `username` como claim adicional
  - `iat`/`exp` (expiración configurable con `JWT_EXPIRATION`, default 86400 s = 24 h)
- El login devuelve *"Credenciales incorrectas"* tanto si el usuario no existe como si la contraseña falla, **sin revelar cuál de los dos datos era el erróneo**.

## Eventos publicados (topic `user-events`)

| Evento | Payload |
|--------|---------|
| `user.registered` | `{ userId, username }` |
| `user.deactivated` | `{ userId, username }` |

Publicados por `UserEventPublisher` (bean condicionado a `app.events.enabled=true`). En tests, el publicador es nulo por lo que no se toca Kafka.

## Estructura de paquetes

```
com.marcmarco.auth
├── AuthApplication.kt      ← punto de entrada (scan shared + auth)
├── config/
│   ├── PasswordConfig.kt   ← BCryptPasswordEncoder
│   └── SecurityConfig.kt   ← filtro de seguridad JWT
├── dto/                    ← RegisterRequest, LoginRequest, LoginResponse,
│                             UserResponse, UpdateProfileRequest, ChangePasswordRequest,
│                             UpdateEmailRequest, UpdateUsernameRequest, DeleteAccountRequest
├── event/UserEventPublisher.kt ← publicador Kafka de eventos de usuario
├── security/
│   ├── AuthService.kt      ← validación de credenciales + emisión de JWT
│   └── JwtUserId.kt        ← extensión para leer `sub` del JWT
└── user/
    ├── User.kt             ← entidad JPA
    ├── UserRepository.kt   ← Spring Data JPA
    ├── UserService.kt      ← lógica de negocio + publicación de eventos
    └── UserController.kt   ← REST API
```

## Configuración relevante (`application.yml`)

| Variable | Default | Uso |
|----------|---------|-----|
| `AUTH_DB_URL` | `jdbc:postgresql://localhost:5433/authdb` | Datasource |
| `AUTH_DB_USERNAME` / `AUTH_DB_PASSWORD` | `postgres` | Credenciales BD |
| `JWT_SECRET` | `dev-only-jwt-secret-cambiar-antes-de-produccion` | Clave HS256 |
| `JWT_EXPIRATION` | `86400` | Segundos de validez del token |
| `KAFKA_BOOTSTRAP` | `localhost:9092` | Broker |
| `EVENTS_ENABLED` | `true` | Activa el publicador Kafka |
